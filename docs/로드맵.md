## 0. 스터디 규칙 → 내 작업에 미치는 영향

이슈 3항목은 `작업 내용` / `Deep Dive 해본 것` / `알게된 것` 입니다. 여기서 나오는 실질적 제약:

- **Deep Dive가 이슈의 중심.** "이번 주 뭘 만들었다"는 1/3이고, 나머지 2/3는 **하나를 깊게 판 기록**.
  → 매주 **"깊게 팔 주제 1개"를 미리 정해놓고** 작업하는 게 유리. 만들다 보면 자동으로 생기지 않음.
- **토론은 설계의 전제·근거·트레이드오프를 겨냥.** 다른 참가자가 물을 질문을 미리 상정하고 작업.
- **실패 사례일수록 큰 학습.** naive 구현 → 측정 → 개선 흐름이 이 스터디 포맷과 정확히 맞음.
  → 각 주차마다 **"순진한 버전을 일부러 먼저 만들고 측정한다"**를 기본 루틴으로.

### Week 01에서 확인한 것 — 다른 참가자들의 수준
- **측정 표와 근거가 있는 글**이 통하는 분위기 (최선규: 실행계획·before/after 표·"도입하지 않은 것"까지)
- **소스 추적 수준의 깊이**도 나옴 (지훈: Node.js 빌드 파이프라인 경로 추적)
- **AI와의 협업 과정 자체**를 사례로 쓰기도 함 (강현우: AI로 DB 설계 후 검토)
- → 우리 강점은 **"측정·검증으로 LLM 답을 반증한 기록"**. 이 축을 계속 가져간다.

### Week 01 — 백엔드 골격 ✅ 완료

**만든 것**: 서비스 정의 → ERD → SQLModel 3테이블 → 시뮬레이터(random walk + 상태 머신) → lifespan 연결

**Deep Dive (제출)**: LLM 답을 검증한 3가지 방법
1. ORM이 만든 SQL을 직접 본다 (`echo=True`) → SQLAlchemy Enum이 **이름**을 저장, CHECK 제약 꺼짐
2. 시간에 따라 상태를 찍어본다 → 상태 머신 도달 불가 분기, 경계 반사 공식 뒤바뀜
3. 통설을 내 데이터로 재본다 → `slots` 메모리 절감 40~50%설 → 실측 17%

**남긴 baseline**: tick 1회 1.91ms(1,000대) / 5.36ms(5,000대) / 23.07ms(20,000대)

**산출물**: [PR #1](https://github.com/One-HyeWon/fleet-ops/pull/1) · `docs/ERD.md` · `docs/용어사전.md`

### Week 02 — 백엔드 완성 (진행 중)

**① 만들 것**
- [ ] `WebSocket /ws/telemetry` — 브로드캐스트, 끊긴 소켓 정리
- [ ] 메모리 → **5초 배치 저장** ⭐
- [ ] REST `GET /robots`, `GET /robots/{id}/telemetry`
- [ ] `docker-compose.yml` (api 서비스, SQLite 볼륨, hot-reload)
- [ ] seed 스크립트 + README

**② 깊게 팔 후보** (1순위 ⭐)

1. **⭐ 쓰기 부하: 매 tick INSERT vs 메모리+배치**
   - 로봇 5,000대 × 100ms tick = **초당 5만 INSERT**.
   - 파볼 것: 트랜잭션으로 묶기(개별 commit이 느린 진짜 이유 = **fsync**), `executemany`,
     SQLite **WAL 모드**, 배치 주기와 **데이터 해상도의 트레이드오프**,
     **샘플링(데이터를 버림) vs 버퍼링(쓰기를 몰아침)** 중 무엇을 택했나.
   - 측정 그림: naive(매 tick commit) 1분 → 배치 1분 → **INSERT/s, 소요시간, DB 파일 크기** 비교표.
2. **WebSocket 브로드캐스트 팬아웃**
   - Week 01에서 미리 계산해둔 것: 로봇 1,000대 전 필드 = **251.8KB/회 → 초당 2.46MB**,
     필요한 필드만 반올림하면 81.2KB → 0.79MB (**68% 절감**).
   - 파볼 것: 끊긴 소켓 정리(안 하면 리스트가 샘), **backpressure**(느린 클라 하나가 전체를 막음),
     직렬화를 클라마다 반복 vs 한 번 만들어 재사용, **변하는 것/안 변하는 것 분리**(name·type은 접속 시 1회만).
3. **FastAPI에서 백그라운드 루프를 어디에 다나** — Week 01에서 절반 다룸(lifespan, `create_task`).
   남은 것: 이벤트 루프 블로킹, 동기 DB 드라이버를 async 세계에서 다루는 법(`asyncio.to_thread`).

**③ 예상 질문**
- "배치 주기 5초는 어떻게 정했나? 서버가 죽으면 그 5초는 날아가는데 괜찮은가?"
- "메모리에 5,000대 상태를 들고 있으면 서버를 2개로 못 늘리는데, 인정하고 가는 건가?"
- "SQLite로 시작한 게 5주차 이전 비용을 키우는 것 아닌가?"

### Week 03 — 프론트 실시간 파이프라인

**① 만들 것**: WS 수신 → Jotai → 렌더, 가상화 데이터그리드(50,000행), **baseline 측정**

**② 깊게 팔 후보**

1. **⭐ 초당 수천 업데이트 → React 리렌더 폭발**
   - 순진한 버전: `useState`에 로봇 배열 통째로 → 로봇 1대 움직여도 **전체 리렌더**.
   - 파볼 것: Jotai `atomFamily`로 로봇당 원자 분리, "왜 Context는 이 문제를 못 푸나"(값이 바뀌면 구독자 전원 리렌더).
   - 측정: React DevTools Profiler로 **커밋 횟수 / 커밋당 시간** before-after.
2. **WS 메시지 배칭 — 네트워크 tick과 렌더 tick 분리**
   - 서버가 100ms마다 보내도 브라우저는 16.6ms마다 그림. `requestAnimationFrame` 기준 병합,
     throttle vs debounce vs 프레임 병합의 차이.
3. **가상화가 실제로 무엇을 아끼나** — 화면 밖 행을 안 만드는 것 vs 만들고 숨기는 것.

**③ 예상 질문**
- "atom을 로봇 수만큼 만들면 atom 자체의 오버헤드는? 5,000개는 괜찮나?"
- "60fps로 못 그릴 바엔 서버 tick을 늦추는 게 낫지 않나 — 어디서 버려야 하나?"

### Week 04 — 3D 대용량 렌더 ★ 포트폴리오 핵심 (절대 밀리면 안 됨)

**① 만들 것**: R3F 3D 뷰, 인스턴싱·LOD·프러스텀 컬링, 1,000대 60fps / 5,000대 30fps

**② 깊게 팔 후보**

1. **⭐ draw call 1000 → 1 (InstancedMesh)**
   - `<mesh>` 1,000개 = **draw call 1,000회** = CPU가 GPU에 1,000번 명령. 이게 병목.
   - 파볼 것: `instanceMatrix` 직접 갱신, "색을 다르게 하려면 왜 `instanceColor`가 따로 필요한가".
   - 측정: r3f-perf로 **draw calls / fps** before-after — 이 표가 포트폴리오 대표 이미지.
2. **R3F에서 React state를 쓰면 안 되는 지점**
   - 위치를 `useState`에 넣고 매 프레임 `setState` = 초당 60번 렌더 트리 순회.
   - `useFrame` 안에서 `ref.current.position` **직접 mutate**(React 렌더 사이클 우회),
     "선언형 React와 명령형 애니메이션의 경계를 어디에 긋나" ← 토론감으로 좋음.
3. **100ms tick을 60fps로 부드럽게 (보간)**
   - lerp 보간. **보간은 "없는 데이터를 지어내는 것"인데 관제 대시보드에서 허용되나** —
     시각적 부드러움 vs 데이터 정확성.
4. **LOD·프러스텀 컬링** — 언제 이득이고 언제 오히려 손해인가.

**③ 예상 질문**
- "인스턴싱하면 개별 로봇 클릭 판정은 어떻게 하나?" (raycasting + instanceId)
- "5,000대에서 30fps면 성공인가 실패인가 — 기준은 누가 정했나?"

### Week 05 — Postgres 이전

**① 만들 것**: docker `db` 서비스, SQLite→Postgres 마이그레이션, 시계열 집계, (stretch) GraphQL

**② 깊게 팔 후보**

1. **⭐ SQLite vs Postgres — 동시성 모델의 차이**
   - SQLite: **파일 락**(쓰기 1개만). Postgres: **MVCC**(읽는 사람이 쓰는 사람을 안 막음).
   - 파볼 것: 왜 Week 01~02엔 SQLite로 버텼나(=쓰기가 배치 하나뿐이라 경합이 없었음),
     동시 쓰기가 생기는 순간 무엇이 깨지는가, SQLite 동적 타입의 함정.
2. **Week 01에서 미뤄둔 숙제 확인**
   - CHECK 제약 이름이 `robots`/`telemetry` 양쪽에 `robotstatus`로 중복.
     PG에선 `sa.Enum`이 **공유 타입**을 만들어 동작이 달라짐. 어떻게 되는지 확인.
   - SQLite에서 FK가 실제로 켜져 있었는지 → 고아 데이터가 없는지 검증.
3. **마이그레이션 자체를 사례로** — Alembic 도입, 기존 데이터 이전, 다운타임.
4. **시계열 집계 & 쿼리 튜닝** — `EXPLAIN ANALYZE` 읽는 법, 다운샘플링 사전 계산 vs 조회 시 계산.
5. **(stretch) REST vs GraphQL 과다수신** — 시간 없으면 **버려도 되는 항목**.

**③ 예상 질문**
- "처음부터 Postgres로 갔으면 이 주차가 필요 없었는데, 낭비 아닌가?"
  → 학습 목적 vs 실무 판단을 분리해서 답할 준비.
