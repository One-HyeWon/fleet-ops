# [Week 02] 조혜원 - 배치 저장은 왜 빨랐나 (fsync가 아니었다)

> 스터디 레포 Issue 제출용 초안. 3항목 형식.
> 상세 근거는 PR 본문과 커밋 히스토리에 있고, 여기엔 압축본만 둔다.

---

## 작업 내용

FleetOps 백엔드를 실시간으로 굴러가게 만들었습니다. 로봇 1,000대가 100ms마다
움직이고, 그 상태를 WebSocket으로 브라우저에 밀어넣으면서 동시에 DB에 남깁니다.

- **배치 저장** — 메모리 버퍼 → 5초마다 `executemany` → 워커 스레드에서 flush
- **WebSocket** `/ws/telemetry` — 100ms 스냅샷 브로드캐스트, 81KB/회
- **REST** — `/robots`(메모리), `/robots/{id}/telemetry`(DB)
- **Docker** — Dockerfile + compose (Week 05에 Postgres, Week 06에 Nginx가 붙을 자리)

설계의 축은 하나입니다. **"지금 어디 있나"는 메모리에, "어디 있었나"는 DB에.**
그래서 `/robots`는 메모리를 읽고 `/robots/{id}/telemetry`는 DB를 읽습니다.

### 통신 방식 — 발표 때 제 근거가 틀렸습니다

지난 스터디에서 "WebSocket이 정말 필요한가, SSE + HTTP면 되지 않나"는 지적을
받았습니다. 그때 제가 댄 근거는 "프론트에서 상태 변경 요청을 보내니 양방향"
이었는데, **지금 코드에 그 요청은 없습니다.** `receive_text()`는 끊김을
감지하려고 대기만 합니다. 지적이 맞았습니다.

다시 정리한 근거는 이렇습니다.

- **현재 스코프만 보면 SSE가 맞습니다.** 서버→클라 단방향이고, SSE는 브라우저가
  자동 재연결까지 해줍니다(WS는 직접 짜야 함).
- 그럼에도 WS를 유지하는 이유는 Week 03~04에 있습니다.
  ① **뷰포트 기반 구독** — 로봇이 늘면 "카메라에 보이는 것만" 보내야 하고,
     그러려면 클라가 카메라를 움직일 때마다 서버에 알려야 합니다. SSE로 하면
     별도 POST + 세션 ID 매칭을 손으로 재구현해야 합니다.
  ② **바이너리 프레임** — 81KB를 더 줄이는 다음 단계인데, SSE는 텍스트 전용이라
     base64를 거치며 **크기가 33% 늘어납니다.**

회의 결론("실시간이라는 한 단어로 묶지 말 것")을 제 기준으로 옮기면 이렇습니다.

> 판단 기준은 "실시간이냐"가 아니라 **"클라이언트가 서버에 지속적으로 말을 거느냐"**.
> LLM 토큰 스트리밍·주식 시세·로그 뷰어가 전부 SSE인 이유가 이것.

**이 판단이 옳았는지는 Week 03에 측정으로 답하겠습니다.** 뷰포트 구독을 실제로
만들면서 SSE 대비 트래픽·구현 복잡도를 재는 것이 다음 주 Deep Dive 후보입니다.

## Deep Dive 해본 것

### 배치 저장이 빠른 건 fsync 때문이 아니었다

**통설**: 매 tick commit이 느린 이유는 커밋마다 `fsync`가 일어나서다.
그러면 트랜잭션으로 묶는 것만으로 해결돼야 합니다.

**그래서 축을 셋으로 쪼개서 쟀습니다.** 하나로 뭉뚱그리면 "배치가 N배 빠르다"
까지만 말할 수 있고, 느린 원인이 DB인지 내 코드인지는 답하지 못합니다.

| 방식 | 행 수 | 소요(s) | ms/tick | peak RSS | DB(MB) |
|---|---:|---:|---:|---:|---:|
| A 매 tick commit | 600,000 | 53.61 | 89.34 | 59 MB | 83.4 |
| B 전체 1 트랜잭션 | 600,000 | 65.56 | 109.26 | **1,300 MB** | 151.8 |
| B' 50tick마다 commit | 600,000 | 43.04 | 71.74 | 245 MB | 95.4 |
| **C executemany** | 600,000 | **9.91** | **16.52** | 59 MB | 95.4 |
| D 5초 샘플링 | 12,000 | 0.69 | 1.14 | 59 MB | **6.0** |

> 로봇 1,000대 × 600 tick, 3회 중앙값, WAL, sleep 없음(최대 속도)
> M-series 맥북 / macOS 26.6 / Python 3.12.8 / SQLite 3.47.2

**B와 C의 커밋 주기를 일부러 똑같이 맞췄습니다.** 그래야 A→B'가 fsync 축,
B'→C가 ORM 축으로 분리됩니다.

**결과: 커밋은 전체 비용의 1%였습니다.**

```
ORM add + commit   (1,000행)   44.6ms
ORM add + flush    (커밋 안 함)  44.2ms    ← 차이 0.4ms
```

커밋 주기를 1/50로 줄여도 1.2배밖에 안 빨라졌고, **5.4배는 전부 ORM 우회에서**
나왔습니다. 44.2ms의 내역은 `Telemetry(**row)` 객체 생성 21.7ms +
(변경추적 등록 + SQL 컴파일) 22.5ms 입니다. `Telemetry(**row)`는 21.7µs/개,
`dict`는 0.16µs/개로 **135배** 차이입니다.

Pydantic 검증이 여기 포함되는데, 검증 대상이 **방금 제가 계산한 숫자**입니다.
검증은 바깥에서 온 데이터에 하는 것이지 내부 계산 결과에 하는 게 아닙니다.

### 예측이 두 번 틀렸고, 틀린 쪽이 더 배울 게 많았다

사전에 primitive 비용을 재서 예측식을 세웠습니다.
`tick 0.92ms + 객체생성 21.7µs×1000 + fsync` → **45.5ms/tick 예상**.

**❌ 틀림 1: 실측 89.3ms/tick (2배)**
사전 측정이 **빈 DB** 기준이었습니다. tick이 쌓이면 인덱스가 커지면서 INSERT가
비싸집니다(20 tick일 때 58.7ms → 600 tick일 때 89.3ms).
→ **1회 측정을 규모로 외삽하면 틀린다.**

**❌ 틀림 2: B가 A보다 느림 (0.8배)**
"트랜잭션을 키우면 최소한 손해는 아니다"라고 봤는데 아니었습니다. 60만 객체가
세션에 살아남아 peak RSS **1.3GB**. GC 압력과 flush 시 세션 전체 순회 비용이
fsync 절감분(tick당 0.4ms)을 넘겼습니다.
→ **fsync를 아끼려고 트랜잭션을 키웠더니 메모리로 되갚았다.**

덤으로, A(83.4MB)가 B(151.8MB)보다 **작습니다.** A는 커밋마다 WAL이
checkpoint되어 본 파일로 접히는데 B는 트랜잭션이 안 끝나 WAL이 계속 자랍니다.
**커밋을 미루면 디스크를 더 씁니다.**

### 처리량과 지연은 다른 축이다

위 표는 **처리량**만 잽니다. 그런데 C로 5초치(5만 행)를 한 번에 넣으면
**1,095ms**가 걸리고(max 7.8s), 동기 DB 드라이버라 그 동안 이벤트 루프가
통째로 멈춥니다. 시뮬레이터도 WebSocket도 `/health`도 정지합니다.

10ms마다 깨어나기로 한 코루틴이 실제로 언제 깨어났는지 재는 heartbeat 방식으로
측정했습니다(Node.js의 event loop lag와 같은 개념).

| 방식 | 지연 중앙값 | p99 | **최대** | tick 밀림 최대 |
|---|---:|---:|---:|---:|
| 직접 호출 | 1.08ms | 17.7ms | **3,999.8ms** | 3,871ms |
| `asyncio.to_thread` | 1.07ms | **25.5ms** | **65.0ms** | 없음 |

**최악 지연 61배 개선. 그런데 p99는 나빠졌습니다.**

SQLite의 C 코드는 GIL을 놓지만 SQL 컴파일·파라미터 바인딩은 파이썬이라 GIL을
잡습니다. 그 조각이 메인 스레드에 잔 지터로 퍼집니다.

> `to_thread`는 느림을 없앤 게 아니라 **드문 대형 정지를 잦은 소형 지터로 바꾼
> 거래**입니다. 100ms tick과 60fps 화면에는 압도적으로 유리한 거래입니다
> (25ms 지터는 안 보이고, 4초 정지는 장애로 보입니다).

**처리량 표만 봤다면 이 차이를 영영 못 봤습니다.**

### 그런데 배치만으로는 부족했다 — 죽음의 나선

여기까지 구현하고 서버를 오래 켜둔 채 부하를 걸었더니 죽었습니다.

```
가동 6분 22초
  telemetry 3,651,000행 / DB 482MB + WAL 107MB
  flush 소요: 10.5s → 24.0s → 18.8s → ... → 44.0s   (배치 주기는 5초)
  버퍼 초과로 1,429,000행 폐기 / COUNT(*) 한 번에 57초
```

flush가 주기를 넘기면 → 버퍼가 더 쌓이고 → 다음 flush가 더 크고 → 더 느려집니다.
되돌아오지 못합니다.

원인은 이렇습니다.

> **배치(버퍼링)는 "어떻게 쓰느냐"를 고칠 뿐 "얼마나 쓰느냐"는 못 고친다.**
> 초당 1만 행을 계속 만들어내면 어떤 쓰기 전략으로도 결국 밀린다.

위 표의 D열(60만 행 → 1.2만 행)이 왜 필요했는지가 여기서 드러났습니다.
`executemany`가 5.4배 빨라도 **5.4배까지만** 버티는 겁니다.

그래서 손잡이를 둘로 분리했습니다. 둘 다 "배치"라는 말로 뭉뚱그려지지만
다른 층의 결정입니다.

| | 무엇을 정하나 | 잃는 것 |
|---|---|---|
| `BATCH_INTERVAL_SEC` (5초) | 얼마나 **몰아서 쓰나** (버퍼링) | 서버가 죽으면 최대 5초치 |
| `TELEMETRY_SAMPLE_EVERY_TICKS` (10) | 얼마나 **자주 남기나** (샘플링) | 샘플 사이의 움직임 |

1초 해상도로 바꾼 뒤 3분 지속 부하 재검증:

| | 매 tick 기록 | 1초 샘플링 |
|---|---|---|
| 폐기 | 1,429,000행 | **0행** |
| flush | 10~44초 | 0.2~1.2초 |
| DB(6분 환산) | 589 MB | **61 MB** |
| WS 프레임 수신률 | — | 98.8% (1778/1800) |

**잃은 것**: 1초 사이의 움직임. "지난 1시간 경로"는 1초 간격 점을 이으면
충분하지만 "충돌 직전 0.3초에 뭐가 있었나"는 데이터가 없습니다. 실시간 화면은
어차피 메모리에서 나오므로 영향 없습니다.

부끄러운 부분도 적어둡니다. `state.py`에 **"DB에는 5초마다 스냅샷만 저장한다"**고
제가 이미 써놨는데 구현이 그걸 따르지 않았습니다. 문서가 맞았습니다.

## 알게된 것

**1. 통설을 인용하기 전에 내 환경에서 재본다.**
"매 tick commit이 느린 건 fsync 때문"은 널리 쓰이는 설명이고 실제로 어떤
환경에서는 맞습니다. 하지만 macOS + WAL + SQLite에서는 커밋이 비용의 1%였습니다.
같은 말을 근거 없이 옮겼다면 엉뚱한 곳을 최적화했을 겁니다.

**2. 예측을 먼저 적어두면 측정이 판정이 된다.**
예측 없이 재면 "C는 9.9초였다"는 그냥 숫자입니다. 예측을 적어두면 맞았을 때
"내 모델이 옳다"는 근거가 되고, 틀렸을 때 **틀린 이유가 곧 배울 내용**이
됩니다. 이번엔 두 번 틀렸고 그 둘이 이 글의 절반입니다.

**3. 처리량과 지연은 같이 안 움직인다.**
`executemany`는 처리량 1위인데 최악 지연도 1위였습니다. "빠르다"고 말할 때
어느 축인지 붙이지 않으면 반쪽만 본 겁니다.

**4. 최적화에는 층이 있고, 아래층이 안 되면 위층은 소용없다.**
쓰기 방식(ORM→executemany)과 쓰기 위치(루프→워커 스레드)를 다 고쳐도,
**생성량 자체**를 안 줄이면 시간 문제였습니다. 배치는 문제를 늦출 뿐이었습니다.

**5. 조용한 실패가 제일 무섭다.** — 실제로 두 번 당했습니다.
- `@event.listens_for(Engine, "connect")`는 Engine **클래스 전역**에 걸립니다.
  `app.db`를 간접 import만 해도 벤치의 별도 엔진까지 FK가 켜져서 INSERT가
  전멸했는데, **측정 숫자는 멀쩡히 나왔습니다.** DB 파일이 24KB인 걸 보고서야
  알았습니다. → 벤치 결과를 믿기 전에 기대한 데이터가 들어갔는지 확인할 것.
- asyncio 태스크의 예외는 아무도 `await` 안 하면 삼켜집니다. `run_persister`가
  죽었는데 서버는 `/health`에 200을 주고 시뮬레이터도 돌았습니다. DB만 안 쌓였고요.

**6. 인메모리 상태는 취향이 아니라 측정의 귀결이었다.**
지난 스터디에서 "인메모리를 많이 쓰면 수평 확장에 불리하다"는 지적을 받았고,
가장 아팠습니다. 이번 측정이 그 답이 됐습니다.

> 인메모리라서 확장이 안 되는 게 아니라, **초당 1만 갱신을 감당하려고 인메모리를
> 택했고 그 대가가 확장 불가**입니다.

지금은 **단일 프로세스 전제**를 명시하는 것을 답으로 삼습니다. 늘리려면 Redis
같은 외부 상태 저장소가 필요하고, 그때 이 숫자들이 그 결정의 근거가 됩니다.

## 아직 못 한 것 (정직하게)

- **backpressure** — 브로드캐스트가 순차 전송이라 느린 클라 하나가 전원을
  기다리게 하고 tick까지 밀립니다. 클라 20개에서 최대 453ms 관측(주기는 100ms).
- **중복 에러 알림 묶기** — 지난 피드백 항목인데 미설계입니다. `Alert` 테이블만
  있고 생성 로직이 없습니다. 같은 이벤트 판정 기준(로봇 ID + 타입 + 시간 윈도우?)과
  이미 발송한 범위 추적을 다음에 설계합니다.
- **MQTT 검토** — 미착수.
- **재현성 한계** — B'는 3회 중앙값 43.0s였지만 단독 재측정에선 78.6s가
  나왔습니다(GC 타이밍 편차). B' 수치는 신뢰구간이 넓습니다. A/C는 재측정에서도
  56.4s / 13.9s로 안정적이었습니다.
- **내구성 트레이드오프** — macOS의 `fsync()`는 드라이브 캐시를 비우지 않습니다.
  진짜 배리어(`F_FULLFSYNC`)를 켜면 0.101ms → 5.185ms로 **51배** 느려집니다.
  텔레메트리 로그라 안 켜는 것을 택했지만, 결제 데이터였다면 켜야 합니다.
  **판단이지 무지가 아니어야 한다**는 점에서 적어둡니다.
