# Part 1. 데이터를 저장한다는 것

## 1-1. 왜 그냥 파일에 저장하면 안 되나

로봇 1,000대의 정보를 저장한다고 해봅시다. 제일 단순한 방법은 텍스트 파일입니다.

```
robots.txt
R-001, 12.5, 30.2, 87
R-002, 45.1, 11.9, 42
...
```

작동은 합니다. 그런데 이런 요구가 들어오는 순간 무너집니다.

| 요구 | 파일로 하면 |
|---|---|
| "배터리 20% 미만인 로봇만 보여줘" | 100만 줄을 전부 읽어서 하나씩 비교 |
| "R-500의 배터리를 43으로 바꿔줘" | 파일 전체를 읽고 → 고치고 → 전체를 다시 씀 |
| 두 명이 동시에 수정하면 | 나중에 쓴 사람이 앞사람 걸 덮어씀 (데이터 유실) |
| 쓰는 도중 전원이 나가면 | 파일이 반쯤 망가진 채로 남음 |
| "로봇이 지워지면 그 로봇의 기록도 정리돼야 해" | 직접 챙겨야 함. 빠뜨리면 유령 데이터 |

**이 다섯 가지를 대신 해결해주는 프로그램이 데이터베이스입니다.**
빠른 검색 · 부분 수정 · 동시 접근 제어 · 장애 복구 · 무결성. 이게 DB가 파는 상품이에요.

## 1-2. 세 단어를 구분하기 — DB / DBMS / SQL

여기가 질문의 핵심입니다. 일상에서는 셋을 뭉뚱그려 "DB"라고 부르지만, 실제로는 층이 다릅니다.

### 도서관 비유

| | 도서관으로 치면 | 실제 |
|---|---|---|
| **데이터베이스 (DB)** | 서가에 꽂힌 **책들 자체** | 저장된 데이터 (파일 `fleet.db` 안의 내용) |
| **DBMS** | 책을 찾아주고 정리하는 **사서** | 프로그램. **SQLite, PostgreSQL, MySQL** |
| **SQL** | 사서에게 건네는 **주문서 양식** | 언어. `SELECT * FROM robots` |

> **데이터베이스**는 *데이터의 집합*이고,
> **DBMS**(DataBase Management System)는 *그걸 관리하는 소프트웨어*이고,
> **SQL**은 *DBMS에게 시키는 말*입니다.

당신이 "PostgreSQL을 쓴다"고 하면 정확히는 **DBMS를 고른 것**입니다.
"DB에 저장한다"고 하면 **데이터를 넣는 것**이고요.
"SQL을 짠다"는 **명령문을 작성하는 것**입니다.

### 왜 이 구분이 실제로 중요한가

- **DBMS는 갈아끼울 수 있고, SQL은 대체로 그대로 갑니다.** 그래서 5주차에 SQLite → PostgreSQL 이전이 가능해요. 사서만 바꾸는 거지 주문서 양식은 거의 같습니다.
- 하지만 **"거의"** 입니다. DBMS마다 문법·타입·동작이 미묘하게 달라서, 그 차이가 5주차 Deep Dive 주제가 됩니다.

### SQLite vs PostgreSQL — 미리 감만

둘 다 관계형 DBMS인데 형태가 완전히 다릅니다.

| | **SQLite** | **PostgreSQL** |
|---|---|---|
| 비유 | 내 방의 **책장** | 사서가 상주하는 **도서관 건물** |
| 형태 | **파일 하나** (`fleet.db`) | 별도로 **떠 있는 서버 프로그램** |
| 접속 | 프로그램이 그 파일을 직접 염 | 네트워크로 접속 (주소·포트·계정) |
| 설치 | 없음. 파이썬에 내장 | 설치하고 실행해둬야 함 (그래서 Docker) |
| 동시 쓰기 | 한 번에 **한 명만** | 여러 명 동시에 |
| 언제 | 개발 초기, 1인용, 모바일 앱 | 실서비스 |

**"내 프로그램 안에 들어 있는 책장"이 SQLite, "밖에 따로 서 있는 건물"이 PostgreSQL.**
2주차에 SQLite로 시작하는 이유가 이겁니다 — 설치도 실행도 필요 없이 파일 하나로 바로 시작.

### (참고) NoSQL은 뭔가
"표 형태가 아닌 DB"들의 통칭입니다. MongoDB(문서), Redis(키-값) 등.
표로 딱 떨어지고 관계가 중요한 데이터엔 관계형이 유리해서, 우리는 관계형으로 갑니다.

## 1-3. 관계형 데이터베이스 = 엑셀 표

우리가 쓸 **관계형 DB(Relational Database)** 는 데이터를 **표**로 저장합니다. 엑셀 시트를 떠올리면 정확합니다.

```
                      robots 테이블
        ┌──────┬─────────┬────────┬─────────┐
 컬럼 → │  id  │  name   │ status │ battery │   ← 열(column) = 속성
        ├──────┼─────────┼────────┼─────────┤
 행   → │  1   │ R-001   │ moving │   87    │   ← 행(row) = 데이터 한 건
        │  2   │ R-002   │ idle   │   42    │
        │  3   │ R-003   │ error  │   12    │
        └──────┴─────────┴────────┴─────────┘
```

| 용어 | 뜻 | 엑셀로 치면 |
|---|---|---|
| **테이블 (table)** | 같은 종류 데이터를 담는 표 하나 | 시트 |
| **행 (row / 레코드)** | 데이터 **한 건** (로봇 한 대) | 가로 한 줄 |
| **컬럼 (column / 필드)** | 데이터의 **속성** (이름, 배터리) | 세로 한 칸 |
| **스키마 (schema)** | 표의 **설계도** — 어떤 컬럼이 어떤 타입인지 | 머리글 행의 정의 |

엑셀과 결정적으로 다른 점: **컬럼마다 타입이 고정**입니다. `battery` 컬럼에 "안녕"을 넣으면 거부당해요. TS의 타입과 같은 역할인데, **실행 중에 실제로 막아준다**는 게 다릅니다.

## 1-4. 기본키와 외래키 — "관계형"의 관계

### 기본키 (Primary Key, PK)
**그 행을 유일하게 가리키는 값.** 주민등록번호 같은 것.

`robots` 테이블에서 `id`가 PK입니다. 이름은 겹칠 수 있어도 id는 절대 안 겹쳐요.
PK가 있어야 "3번 로봇을 수정해줘"가 가능합니다.

### 외래키 (Foreign Key, FK)
**다른 테이블의 행을 가리키는 값.**

로봇의 이동 기록을 저장한다고 해봅시다. 이렇게 하면 안 됩니다:

```
telemetry 테이블 (나쁜 예 — 로봇 정보를 통째로 복사)
┌────┬─────────┬────────┬──────┬──────┐
│ id │  name   │ type   │  x   │  y   │
├────┼─────────┼────────┼──────┼──────┤
│ 1  │ R-001   │ robot  │ 12.5 │ 30.2 │
│ 2  │ R-001   │ robot  │ 12.7 │ 30.4 │   ← name, type이 계속 중복
│ 3  │ R-001   │ robot  │ 12.9 │ 30.6 │
└────┴─────────┴────────┴──────┴──────┘
```

로봇 이름을 바꾸면 **수백만 행을 전부 고쳐야** 하고, 하나라도 빠뜨리면 같은 로봇인데 이름이 두 개가 됩니다.

대신 **id로 참조**합니다:

```
robots                          telemetry
┌────┬────────┬───────┐        ┌────┬──────────┬──────┬──────┐
│ id │  name  │ type  │        │ id │ robot_id │  x   │  y   │
├────┼────────┼───────┤        ├────┼──────────┼──────┼──────┤
│ 1  │ R-001  │ robot │◀───────│ 1  │    1     │ 12.5 │ 30.2 │
│ 2  │ R-002  │ drone │   ┌────│ 2  │    1     │ 12.7 │ 30.4 │
└────┴────────┴───────┘   │    │ 3  │    2     │ 88.1 │ 5.0  │
         ▲                │    └────┴──────────┴──────┴──────┘
         └────────────────┘         ↑
                              이게 외래키(FK)
```

`telemetry.robot_id`가 **FK**입니다. "이 기록은 1번 로봇의 것"이라는 의미.

FK를 **제약(constraint)으로 선언**하면 DBMS가 이걸 강제해줍니다:
- 존재하지 않는 로봇 id로 기록을 넣으려 하면 → **거부**
- 기록이 딸린 로봇을 지우려 하면 → **거부** (또는 같이 삭제)

이렇게 **말이 안 되는 데이터가 애초에 못 들어오게 막는 것**을 **참조 무결성(referential integrity)** 이라고 합니다.
"관계형"이라는 이름이 여기서 나왔습니다 — 테이블끼리 관계를 맺으니까요.

> ⚠️ **SQLite의 함정**: SQLite는 FK 제약이 **기본으로 꺼져 있습니다.**
> 선언해도 조용히 무시돼요. 연결할 때마다 `PRAGMA foreign_keys=ON`을 해줘야 실제로 동작합니다.
> 이걸 모르면 "FK 걸었으니 안전하다"고 믿다가 5주차 PostgreSQL 이전 때 터집니다.

### 인덱스 (index)
**책 뒤의 찾아보기(색인).**

"R-500의 기록을 보여줘"를 인덱스 없이 하면 100만 행을 처음부터 끝까지 훑습니다(**풀 스캔**).
인덱스가 있으면 색인을 보고 바로 해당 위치로 점프합니다.

공짜는 아닙니다 — **인덱스도 저장 공간을 먹고, 데이터를 넣을 때마다 색인도 갱신**해야 해서 쓰기가 조금 느려집니다.
그래서 "자주 검색하는 컬럼에만" 겁니다.

# Part 2. SQL — DBMS에게 말 거는 법

## 2-1. SQL이란

**Structured Query Language.** DBMS에게 시키는 **언어**입니다.

파이썬·자바스크립트 같은 범용 언어가 아니라, **오직 데이터를 다루기 위한 전용 언어**예요.
1970년대에 만들어졌고, 지금도 거의 모든 관계형 DBMS가 이 언어를 씁니다.

## 2-2. 핵심 문장 4개 (CRUD)

실무에서 쓰는 SQL의 90%는 이 넷입니다.

```sql
-- 조회 (Read)
SELECT name, battery FROM robots WHERE battery < 20;
   ↑ 어떤 컬럼을    ↑ 어느 표에서   ↑ 어떤 조건으로

-- 삽입 (Create)
INSERT INTO robots (name, battery) VALUES ('R-001', 87);

-- 수정 (Update)
UPDATE robots SET battery = 43 WHERE id = 500;

-- 삭제 (Delete)
DELETE FROM robots WHERE id = 500;
```

읽어보면 거의 영어 문장입니다. **"robots에서 battery가 20 미만인 것의 name과 battery를 골라라."**

`WHERE`를 빼먹으면 **전체 행**에 적용된다는 게 유명한 사고 지점입니다.
`UPDATE robots SET battery = 43;` → 모든 로봇의 배터리가 43이 됩니다.

## 2-3. SQL이 특이한 점 — "어떻게"가 아니라 "무엇을"

이게 SQL을 이해하는 가장 중요한 열쇠입니다.

JavaScript로 "배터리 20% 미만 로봇 찾기"를 쓰면 **절차**를 적습니다:
```js
const result = []
for (const r of robots) {        // 처음부터 하나씩 돌면서
  if (r.battery < 20) {          // 조건을 확인하고
    result.push(r)               // 맞으면 담는다
  }
}
```

SQL은 **결과만** 적습니다:
```sql
SELECT * FROM robots WHERE battery < 20;
```

"어떻게 찾을지"는 안 적혀 있죠. **그건 DBMS가 알아서 정합니다.**
인덱스를 쓸지, 전부 훑을지, 어떤 순서로 조인할지를 DBMS 안의 **쿼리 플래너(query planner)** 가 판단해요.

이런 방식을 **선언형(declarative)** 이라고 합니다. React가 "DOM을 이렇게 조작해라"가 아니라
"화면이 이렇게 생겨야 한다"를 쓰는 것과 같은 사고방식이에요.

> 그래서 성능 튜닝이 독특해집니다. 코드를 고치는 게 아니라 **DBMS가 좋은 계획을 세우도록**
> 인덱스를 만들어주고, 어떤 계획을 세웠는지 `EXPLAIN`으로 들여다봅니다. (5주차 주제)

## 2-4. 트랜잭션 (transaction)

**"전부 성공하거나, 전부 없던 일이 되거나"** 하는 작업 묶음.

계좌 이체가 교과서 예시입니다. A에서 1만원 빼고 → B에 1만원 넣기.
중간에 서버가 죽으면? 돈이 증발합니다. 그래서 둘을 하나로 묶습니다.

```sql
BEGIN;                                        -- 묶음 시작
  UPDATE accounts SET balance = balance - 10000 WHERE id = 'A';
  UPDATE accounts SET balance = balance + 10000 WHERE id = 'B';
COMMIT;                                       -- 확정
```

중간에 문제가 생기면 `ROLLBACK` — 통째로 되돌아갑니다.

**우리 프로젝트에서는**: 5초마다 `telemetry`에 기록을 넣으면서 `robots`의 현재 위치도 갱신하는데,
둘이 반드시 같은 시점이어야 하므로 **한 트랜잭션으로 묶습니다.**

트랜잭션은 성능과도 직결됩니다 → Part 5의 fsync에서 이어집니다.

# Part 3. 파이썬 기본기

## 3-1. 인스턴스 (instance)

클래스로 찍어낸 **객체 하나**. JS와 같은 개념입니다.

```python
class Robot:
    def __init__(self, name):    # JS의 constructor
        self.name = name         # JS의 this.name

r = Robot("R-001")               # r이 "인스턴스"
```
```js
class Robot { constructor(name) { this.name = name } }
const r = new Robot("R-001")     // 파이썬은 new 없이 부름
```

`self`는 JS의 `this`인데, **파이썬은 메서드 첫 인자로 명시적으로 받습니다.**

## 3-2. dict (딕셔너리)

**JS의 객체 / `Map`.** 키-값 쌍의 모음입니다.

```python
robots = {1: "R-001", 2: "R-002"}
robots[1]           # "R-001"     ← 즉시 찾음
robots[3] = "R-003" # 추가
for id, name in robots.items(): ...
```

**왜 배열이 아니라 dict인가**: 실시간 상태는 "3번 로봇을 갱신해줘"가 초당 수천 번 일어납니다.
배열이면 매번 `find`로 훑어야 하고(1,000개면 평균 500번 비교), dict는 **한 번에** 찾습니다.

## 3-3. dataclass

파이썬에서 **"데이터만 담는 클래스"를 짧게 쓰는 문법**입니다.

원래는 이렇게 장황하게 써야 합니다:
```python
class RobotState:
    def __init__(self, id, x, y, battery):
        self.id = id
        self.x = x
        self.y = y
        self.battery = battery
```

`@dataclass`를 붙이면 `__init__`을 **자동 생성**해줍니다:
```python
from dataclasses import dataclass

@dataclass
class RobotState:
    id: int
    x: float
    y: float
    battery: float

s = RobotState(id=1, x=12.5, y=30.2, battery=87)
s.battery = 86            # 그냥 값 바꾸기
```

> **왜 dict 대신 dataclass인가**
> `state["battry"]` 같은 오타는 dict에선 런타임에야 터집니다.
> `state.battry`는 에디터가 즉시 빨간 줄을 그어요. TS를 쓰는 이유와 정확히 같습니다.

`@`로 시작하는 문법을 **데코레이터(decorator)** 라고 합니다. 함수/클래스를 감싸서 기능을 덧붙이는 장치예요.
FastAPI의 `@app.get("/robots")`도 데코레이터입니다.

# Part 4. 검증과 ORM — 이 구간이 제일 헷갈립니다

세 라이브러리가 층층이 쌓여 있습니다. 먼저 지도부터.

```
   SQLModel        ← 우리가 쓸 것. 아래 둘을 합친 것
   ├── Pydantic    ← 데이터 검증기         (zod 자리)
   └── SQLAlchemy  ← ORM                   (Prisma 자리)
```

## 4-1. Pydantic — 런타임 검증기 (≈ zod)

TypeScript의 타입은 **컴파일하면 사라집니다.** 서버가 실행 중일 때 외부에서 이상한 JSON이 들어오면 못 막아요.
그래서 프론트에서도 `zod` 같은 걸로 런타임 검증을 하죠.

Pydantic이 파이썬의 그 자리입니다.

```python
from pydantic import BaseModel

class RobotCreate(BaseModel):
    name: str
    battery: float
```

이렇게 선언해두면 **실행 중에 실제로 검사**합니다. `battery`에 `"많음"`이 들어오면 에러를 냅니다.

FastAPI가 Pydantic을 기본 내장하고 있어서, 이 클래스 하나로:
- 요청 본문 자동 검증
- 잘못된 요청에 자동으로 422 에러 응답
- **API 문서 자동 생성** (`/docs`에 화면이 생김)

이 세 개가 공짜로 따라옵니다. FastAPI가 인기 있는 큰 이유예요.

## 4-2. ORM — 객체 ↔ 테이블 자동 연결 (≈ Prisma)

**Object-Relational Mapping.** 파이썬 **객체**와 DB **테이블 행**을 자동으로 이어주는 도구입니다.

ORM 없이 쓰면 SQL 문자열을 직접 조립합니다:
```python
cursor.execute("INSERT INTO robots (name, battery) VALUES (?, ?)", ("R-001", 87))
row = cursor.execute("SELECT * FROM robots WHERE id = 1").fetchone()
name = row[1]        # 몇 번째가 name인지 외워야 함
```

ORM을 쓰면 객체를 다룹니다:
```python
session.add(Robot(name="R-001", battery=87))
robot = session.get(Robot, 1)
robot.name           # 이름으로 접근
```

**얻는 것**: 타입 안전, 자동완성, SQL 인젝션 방어, DBMS 갈아끼우기 쉬움(5주차!)
**잃는 것**: 뒤에서 어떤 SQL이 나가는지 안 보임 → 나도 모르게 느린 쿼리가 나감 (대표적으로 **N+1 문제**)

> **ORM을 쓴다고 SQL을 몰라도 되는 게 아닙니다.** 오히려 반대로,
> ORM이 만들어낸 SQL을 읽을 줄 알아야 성능 문제를 잡습니다. 이게 좋은 Deep Dive 소재예요.

## 4-3. SQLAlchemy — 파이썬 대표 ORM

Prisma/TypeORM 자리에 있는 물건입니다. 역사가 길고 강력한데 설정이 장황합니다.

## 4-4. SQLModel — 우리가 쓸 것

원래 FastAPI로 개발하면 **같은 구조를 두 번** 써야 했습니다.
테이블 정의용(SQLAlchemy) 한 벌, API 검증용(Pydantic) 한 벌. 컬럼 하나 추가하면 두 군데를 고쳐야 했죠.

**SQLModel은 클래스 하나로 둘 다 합니다.** FastAPI를 만든 사람이 만들었어요.

```python
from sqlmodel import SQLModel, Field

class Robot(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    name: str
    battery: float
```

- `table=True` → "이건 실제 DB 테이블이다"
- `Field(primary_key=True)` → 기본키 지정
- 이 클래스 하나가 **테이블 정의 + 요청 검증 + 응답 직렬화 + API 문서**를 전부 담당

# Part 5. 세션 · flush · 추적

## 5-1. 세션 (Session)

**DB와 대화하는 하나의 작업 공간.** ORM이 "지금 네가 만지는 객체들"을 모아두는 **바구니**입니다.

```python
with Session(engine) as session:     # 바구니 열기
    session.add(robot)               # 바구니에 담기 — 아직 DB엔 안 감!
    session.commit()                 # 이제 진짜 DB에 반영 + 확정
```

핵심: **`add`한 순간엔 DB에 아무 일도 안 일어납니다.** 메모리 바구니에 적어둘 뿐이에요.

`engine`은 "DBMS로 가는 연결 통로"이고, `Session`은 "그 통로로 하는 한 번의 작업 묶음"입니다.

## 5-2. flush vs commit

| | 하는 일 | 되돌릴 수 있나 |
|---|---|---|
| **flush** | 바구니의 변경사항을 **SQL로 만들어 DB에 전송** | 예 (아직 트랜잭션 안) |
| **commit** | flush + **트랜잭션 확정** | 아니오 |

commit이 flush를 포함합니다. 보통은 commit만 쓰면 됩니다.
flush를 따로 알아야 하는 이유는 — 자동으로 일어나기 때문입니다. 다음 항목으로.

## 5-3. 변경 추적 (change tracking)

세션 바구니에 담긴 객체는 ORM이 **계속 감시**합니다.

```python
robot = session.get(Robot, 1)    # DB에서 꺼냄 → 자동으로 바구니에 담김
robot.name = "새이름"             # 그냥 파이썬 변수를 바꿨을 뿐인데
session.commit()                 # ← ORM이 알아서 UPDATE 문을 날림
```

`session.add()`를 부르지 않았는데도 UPDATE가 나갑니다.
ORM이 "꺼낼 때는 이 값이었는데 지금 바뀌었네"를 비교해서 기억해뒀거든요. 이걸 **dirty tracking**이라고 합니다.

**편리하지만 위험합니다.** 세션에 붙은 객체를 무심코 수정하면 의도치 않은 UPDATE가 나가요.

> 그래서 우리 설계에서 이런 이야기가 나옵니다:
> 실시간 로봇 상태는 **100ms마다 값이 바뀝니다.** 이걸 SQLModel 객체로 들고 있으면
> 그 변경이 전부 추적 대상이 되고, 예기치 않은 시점에 DB로 새어나갈 수 있어요.
> → **메모리용 타입(`@dataclass`)과 DB용 타입(`SQLModel`)을 분리**하는 이유입니다.

## 5-4. 메모리 상태 vs DB 행

| | 메모리 상태 | DB 행 |
|---|---|---|
| 어디에 | 서버 프로세스의 **RAM** | **디스크** 파일 |
| 속도 | 즉시 (나노초) | 느림 (밀리초) |
| 서버를 끄면 | **사라짐** | 남아 있음 |
| 프론트로 치면 | Jotai/Zustand store의 값 | 서버에 저장된 값 |

우리 설계: **실시간 위치는 메모리에, 과거 기록만 DB에.** 이 둘을 어떻게 나누느냐가 2주차의 전부입니다.

# Part 6. 실시간 관련

## 6-1. tick (틱)

**일정 간격마다 한 번씩 도는 것.** 게임 루프에서 온 말입니다.

브라우저 `requestAnimationFrame`이 초당 60번 도는 게 렌더 tick 60회죠.
우리 시뮬레이터는 **100ms마다** 모든 로봇 위치를 갱신할 예정 → **초당 10 tick**.

"매 tick INSERT"는 곧 "0.1초마다 DB에 저장"이라는 뜻입니다.

## 6-2. 이벤트 루프와 블로킹

파이썬의 `async`/`await`는 **JS와 같은 구조**입니다 — 단일 스레드에서 도는 **이벤트 루프** 하나.

그래서 JS와 똑같은 함정이 있습니다. 오래 걸리는 작업이 루프를 붙잡으면 **다른 모든 일이 멈춥니다.** 이걸 **블로킹**이라고 해요.

```python
time.sleep(1)          # ❌ 루프 전체가 1초 정지
await asyncio.sleep(1) # ✅ 다른 작업에 자리를 내줌
```

브라우저에서 무거운 `for` 루프를 돌리면 화면이 얼어붙는 것과 같은 현상입니다.

## 6-3. WebSocket

일반 HTTP는 **클라이언트가 물어봐야 서버가 답합니다.** 서버가 먼저 말을 걸 수 없어요.
실시간 데이터를 받으려면 브라우저가 계속 "새 거 있어요?"를 반복해야 하는데(폴링), 낭비가 심하죠.

**WebSocket은 한 번 연결하면 그 통로가 계속 열려 있어서, 서버가 먼저 데이터를 밀어넣을 수 있습니다.**
우리가 100ms마다 로봇 위치를 브라우저로 보낼 방법입니다.

# Part 7. 저장 성능 — 배치와 fsync

## 7-1. fsync — 배치 저장의 진짜 이유

파일에 뭔가 쓰면, OS는 보통 **메모리 버퍼에만 담아두고 "썼다"고 답합니다.** 실제 디스크 기록은 나중에 몰아서 해요. 그래야 빠르니까요.

그런데 그 상태에서 전원이 나가면? **데이터가 사라집니다.**

DB는 "저장했다"고 말한 건 반드시 살아남아야 합니다(이걸 **내구성/durability**라고 합니다).
그래서 **commit할 때마다 `fsync`라는 시스템 콜**을 부릅니다 — "지금 당장 디스크에 진짜로 밀어넣고, 끝나면 알려줘."

이게 **SSD에서도 밀리초 단위**로 느립니다. 물리 장치가 실제로 응답해야 하니까요.

```
5만 건을 한 건씩 commit  →  fsync 5만 번  →  불가능
5만 건을 한 트랜잭션으로  →  fsync 1번    →  순식간
```

> **그래서 "배치 저장"의 본질은 쿼리를 모으는 게 아니라, commit(=fsync) 횟수를 줄이는 것입니다.**
> 이게 이번 주 Deep Dive의 핵심 문장이 될 겁니다.

## 7-2. 배치 저장 (batch write)

**한 건씩 저장하지 않고 모아서 한 번에.**

- 낱개: 로봇이 움직일 때마다 → 초당 수만 번 저장 → 죽음
- 배치: 5초 동안 메모리에 모아뒀다가 → 5초에 한 번 → 살아남음

대가: **서버가 죽으면 마지막 5초는 사라집니다.** 이건 버그가 아니라 **의도한 선택**이고,
"왜 그래도 되는가"를 설명할 수 있어야 합니다.

## 7-3. WAL 모드 (Write-Ahead Logging)

SQLite의 옵션입니다. 원본 DB 파일을 직접 고치는 대신, **변경사항을 별도 로그 파일에 덧붙여 쓰고** 나중에 본체에 합칩니다.

효과: **읽기가 쓰기를 막지 않습니다.** 우리처럼 "가끔 몰아서 쓰고 자주 읽는" 패턴에 딱 맞아요.

# Part 8. 도메인 용어 (관제 시스템)

## 8-1. 텔레메트리 (telemetry)

**tele(멀리) + metry(측정) = 원격 측정.**
멀리 있는 기계가 **자기 상태를 스스로 측정해서 보내오는 신호**를 말합니다.

원래는 로켓·인공위성 용어였습니다. 사람이 따라갈 수 없는 곳에 기계를 보내놓고
"지금 온도 몇 도? 연료 얼마 남았어?"를 알아내려면, 기계가 스스로 보고하는 수밖에 없었죠.

지금은 훨씬 넓게 씁니다:
- **F1 자동차** → 타이어 온도·연료를 실시간으로 피트에 전송
- **의료기기** → 환자 심박·산소포화도를 간호사 스테이션으로
- **서버 모니터링** → CPU·메모리 사용률 (개발자가 제일 자주 만나는 텔레메트리)
- **우리 로봇** → 위치·배터리·속도

**핵심 성질 3가지** — 이게 스키마 설계를 결정합니다.

| 성질 | 뜻 | 설계에 미치는 영향 |
|---|---|---|
| **주기적** | 일정 간격으로 계속 옴 | 양이 폭발적으로 늘어남 → 배치 저장 필요 |
| **한 방향** | 기계 → 서버로만 (명령은 별개) | 우리 스코프: 관제만, 조작 X |
| **불변** | 이미 관측된 과거는 안 바뀜 | append-only → 중복 저장해도 안전 |

> **"측정값"이지 "명령"이 아닙니다.** 로봇이 자기 상태를 보고할 뿐,
> 서버가 로봇에게 뭘 시키는 건 텔레메트리가 아니라 **커맨드(command)** 입니다.
> 우리 프로젝트는 텔레메트리만 다루고 커맨드는 스코프 밖입니다.

## 8-2. 얼럿 (alert)

**"이건 사람이 봐야 한다"고 판정된 사건.**

로봇 1,000대가 매초 숫자를 쏟아내는데, 사람이 그걸 다 볼 수는 없습니다.
그래서 **서버가 대신 감시하다가 규칙에 걸리는 것만 골라서** 사람에게 올립니다. 그게 얼럿이에요.

```
텔레메트리 = 원본 데이터 (초당 1만 건, 대부분 정상)
    ↓ 서버가 규칙으로 걸러냄
얼럿      = 사람이 봐야 할 것만 (하루 몇십 건)
```

**텔레메트리와 얼럿의 결정적 차이:**

| | 텔레메트리 | 얼럿 |
|---|---|---|
| 누가 만드나 | 로봇(기계) | **서버**(판정) |
| 얼마나 | 초당 수천 건 | 드물게 |
| 성격 | 사실 기록 | **해석의 결과** |
| 수정되나 | 절대 안 됨 | 됨 (해소·확인 처리) |

얼럿은 **"판단"이라서 바뀔 수 있습니다.** "배터리 20% 미만은 경고"라는 기준은 사람이 정한 것이고,
내일 15%로 바꿀 수도 있어요. 반면 "그때 배터리가 19%였다"는 사실은 영원히 안 바뀝니다.

> 이 구분 때문에 `telemetry`는 절대 수정하지 않고, `alerts`는 `resolved_at`/`acknowledged`로 **수정합니다.**

## 8-3. heading (방위각)

로봇이 **어느 방향을 바라보고 있는지**를 각도로 나타낸 것. 나침반과 같습니다.

```
        0° (북)
          │
270° ─────┼───── 90° (동)
          │
        180° (남)
```

위치(`x, y`)만으로는 로봇이 어느 쪽을 향하는지 알 수 없습니다.
3D 화면에서 로봇 모델을 **회전시켜 그리려면** 이 값이 필요해요.

## 8-4. 임계값 (threshold) / 상태 전이 (transition)

- **임계값**: 판정 기준선. "배터리 20%" 같은 숫자.
- **상태 전이**: 기준선을 **넘어가는 순간**.

이 둘의 구분이 알림 설계의 핵심입니다.

```
배터리:  25% → 22% → 19% → 17% → 15%
                      ↑
                 여기가 "전이"
              (20% 선을 넘어간 순간)
```

**"19%인 상태"** 는 계속 유지되지만, **"20%를 넘어간 순간"** 은 한 번뿐입니다.
알림을 상태 기준으로 만들면 초당 10개씩 쏟아지고, 전이 기준으로 만들면 딱 한 번 생깁니다.

전자 회로 용어를 빌려 **레벨 트리거(level trigger)** vs **엣지 트리거(edge trigger)** 라고도 부릅니다.
