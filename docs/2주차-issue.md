# [2주차] FastAPI + SQLite 백엔드 골격 & 실시간 텔레메트리 스트림

> 스터디 주차 이슈 · FleetOps 프로젝트
> 구현·비판·회고 섹션은 **주말에 작업 후** 채웁니다. 지금은 배경/고민/설계 + 계획을 먼저 작성.

## 🎯 이번 주 목표
로봇 Fleet의 **실시간 텔레메트리를 생성·전송하는 백엔드**를 세운다. FastAPI로 시뮬레이터(N개 로봇)를 만들고, WebSocket으로 프론트에 실시간 push, DB(SQLite)에 스키마를 설계한다. 로컬은 docker-compose로 띄운다.

## ✅ 할 일 체크리스트
- [ ] `backend/` FastAPI 프로젝트 세팅 (uvicorn, `/health`)
- [ ] SQLModel 모델 정의: `Robot`, `Telemetry`, `Alert` (FK·정합성)
- [ ] 텔레메트리 **시뮬레이터**: N개 로봇 random-walk(위치·배터리·상태) 백그라운드 루프
- [ ] `WebSocket /ws/telemetry` — 연결된 클라에 tick마다 브로드캐스트
- [ ] REST: `GET /robots`, `GET /robots/{id}/telemetry` (과거 조회)
- [ ] 실시간 상태는 **메모리**, DB엔 **주기적 배치 저장**(매 tick 전량 INSERT 금지)
- [ ] `docker-compose.yml` — `api` 서비스(SQLite 파일 볼륨), hot-reload
- [ ] seed 스크립트 + README에 실행법

## 완료 조건 (측정 가능)
- `docker compose up` 한 줄로 백엔드 기동
- WebSocket 접속 시 **1,000개 로봇**이 실시간 스트리밍(브라우저 콘솔/wscat으로 확인)
- `GET /robots` 응답 < 100ms, 과거 telemetry 조회 동작
- 매 tick DB 저장이 아니라 **N초 배치 저장**으로 write 부하 제어됨(로그로 확인)

## 📝 스터디 글 (배경 → 회고)

### 배경 — 무엇을 해결하려 했는가?
관제 대시보드는 "데이터를 어디서 불러오나"가 아니라 **실시간으로 들어오는 텔레메트리**를 다루는 게 본질. 그래서 정적 데이터셋 대신, **직접 시뮬레이터로 대량의 실시간 신호를 생성**하는 백엔드가 먼저 필요했다. (부하를 마음대로 조절해 성능 테스트의 기준을 만들 수 있음)

### 고민 — 왜 어려웠는가 / 제약
- **저장 부하**: 5,000개 로봇을 매 100ms마다 DB에 넣으면 초당 5만 INSERT → DB가 못 버팀. "실시간성"과 "과거 기록"을 어떻게 분리할까?
- **스키마 설계**: 실시간 위치와 시계열 기록, 알림을 어떻게 나눌까? 정합성(FK)은?
- **SQLite로 시작해도 되나**: 동시성 약한 SQLite로 실시간을 감당할까? (→ 실시간은 메모리라 DB 부하는 배치뿐이라 OK. 이전 계획은 5주차.)

### 설계 — 어떤 선택지를 고민했는가
- 실시간 상태: **① 메모리 관리 + 주기적 배치 저장**(채택) vs ② 매 tick DB 저장(탈락, write 폭발) vs ③ Redis(오버스펙, 이번 스코프 밖)
- 테이블 분리: `robots`(현재 상태) / `telemetry`(시계열 기록) / `alerts`(이벤트). FK로 참조 정합성.
- DB: **SQLite**(즉시 시작, 컨테이너 불필요) → 5주차 Postgres 이전.
