## 1. 작업 내용

6주 포트폴리오 프로젝트(**FleetOps** — 로봇 수천 대의 실시간 텔레메트리를 3D로 시각화하는 관제 대시보드)의 백엔드 골격을 만들었다. 이번 주 결과물은 ERD 설계, SQLModel 테이블 3개, 로봇 1,000대를 움직이는 시뮬레이터다.

문제는 **내가 백엔드가 처음**이라는 것이다. React·TypeScript는 실무로 쓰지만 FastAPI·SQLModel·SQLite·asyncio는 이번이 처음이라, LLM 의존도가 평소보다 훨씬 높았다. 그래서 이번 주의 실제 주제는 "백엔드를 만들었다"가 아니라 **"내가 이해하지 못한 영역에서 받은 코드를 어떻게 믿을 것인가"** 가 됐다.

받은 답 중 **4개가 틀렸다.** 전부 "완전히 틀린 답"이 아니라 **"대부분 맞는데 가정 하나가 검증되지 않은 답"** 이었다.

| # | 받은 답 | 실제 | 발견 방법 |
|---|---|---|---|
| 1 | SQLAlchemy가 Enum의 **값**(소문자)을 저장하고 CHECK 제약을 만든다 | **이름**(대문자) 저장, CHECK 없음 | 생성된 DDL 확인 |
| 2 | `@dataclass(slots=True)`는 메모리를 40~50% 줄인다 | 우리 데이터에선 **17%** | `tracemalloc` 측정 |
| 3 | 경계 반사 공식 (x벽 / y벽) | **두 공식이 뒤바뀜** | 로봇 1대의 좌표를 틱마다 추적 |
| 4 | 상태 전이를 `if/elif` 사슬로 | **도달 불가 분기 발생** | 6,000틱 상태 분포 관찰 |

3번과 4번은 **코드를 아무리 읽어도 보이지 않았다.** 문법도 맞고 로직도 그럴듯했다. 실행해서 시간에 따라 관찰해야만 드러났다.

이 글은 그 4개를 어떻게 찾았는지, 그리고 거기서 뽑아낸 **검증 방법 3가지**에 대한 기록이다.

## 2. Deep Dive 해본 것

### 방법 1 — ORM이 만든 SQL을 직접 본다

#### 상황

로봇 상태(`idle`/`moving`/`charging`/`error`/`offline`)를 어떻게 저장할지 물었다. 받은 답은 "SQLite엔 ENUM 타입이 없으니 TEXT로 저장된다. 파이썬 `Enum`을 필드 타입으로 쓰면 SQLAlchemy가 **값을 저장하고 CHECK 제약을 만들어준다**"였다.

그럴듯했다. 그리고 둘 다 틀렸다.

#### 확인

SQLModel(SQLAlchemy)의 엔진 옵션 `echo=True`를 켜면 DB로 나가는 SQL이 전부 로그에 찍힌다. DB 파일을 지우고 다시 생성했다.

```sql
-- 실제로 생성된 DDL
CREATE TABLE robots (
    status VARCHAR(8) NOT NULL,     -- ← CHECK 제약이 없다
    ...
)
```

```python
class RobotStatus(StrEnum):
    MOVING = "moving"      # 값은 소문자인데

# DB에 실제로 들어간 값
'MOVING'                   # 대문자 — 즉 멤버 '이름'
```

#### 원인

1. **SQLAlchemy는 기본적으로 Enum의 `.name`을 저장한다.** `.value`가 아니다.
2. **`CHECK` 제약은 SQLAlchemy 1.4부터 기본이 꺼져 있다** (`create_constraint=False`).

둘 다 **SQLModel 문서에는 없는 동작**이다. SQLModel은 SQLAlchemy(ORM)와 Pydantic(검증)을 합친 얇은 껍데기이고, 실제 DB 작업은 그 아래 SQLAlchemy가 한다. 막히면 SQLModel이 아니라 SQLAlchemy 문서를 봐야 한다는 걸 여기서 알았다.

#### 왜 문제인가 — 기능이 아니라 운영의 문제

파이썬 코드로만 접근하면 ORM이 알아서 변환해주므로 **아무 문제 없이 돌아간다.** 문제는 사람이 DB를 직접 볼 때다.

```sql
-- API 문서에는 status가 "moving" 이라고 돼 있으니 이렇게 친다
SELECT * FROM robots WHERE status = 'moving';
-- → 0건
```

코드 어디에도 `MOVING`이라고 쓴 적이 없으니 원인을 짐작하기 어렵다. 장애 대응 중이라면 더 그렇다. **밖으로 나가는 값과 안에 저장된 값이 다른 것은, 기능은 멀쩡한데 사람이 매번 걸려 넘어지는 종류의 비용이다.**

#### 조치

```python
sa.Enum(
    enum_cls,
    values_callable=lambda e: [m.value for m in e],  # 이름 대신 값
    create_constraint=True,                          # CHECK 생성
)
```

```sql
status VARCHAR(8) NOT NULL,
CONSTRAINT robotstatus CHECK (status IN ('idle','moving','charging','error','offline'))
```

CHECK가 실제로 막는지 확인했다.

```python
c.execute(text("UPDATE robots SET status='dancing'"))
# → IntegrityError
```

#### CHECK를 굳이 켠 이유 — 방어선이 3층이다

```
① 파이썬 Enum  →  개발 중 오타 차단 (에디터가 잡음)
② Pydantic     →  API로 들어오는 값 차단 (422)
③ DB CHECK     →  어떤 경로로 들어와도 차단
```

①②는 **내 파이썬 코드를 통과할 때만** 작동한다. 나중에 데이터 정리한다고 DB에 직접 SQL을 날리거나 마이그레이션 스크립트를 돌리는 순간 무력해진다. ③만이 경로와 무관하다.

같은 이유로 SQLite의 외래키도 확인했다. **SQLite는 FK 제약이 기본으로 꺼져 있어서, 선언해도 조용히 무시한다.** 연결마다 `PRAGMA foreign_keys=ON`이 필요하다. 이것도 모르고 넘어갔으면 "FK 걸었으니 안전하다"고 믿었을 테고, 5주차 PostgreSQL 이전 때 그동안 쌓인 고아 데이터로 터졌을 것이다.

### 방법 2 — 시간에 따라 상태를 찍어본다

여기서 찾은 두 버그는 **정적 리뷰로는 발견이 불가능했다.**

#### 2-1. 도달할 수 없는 분기

로봇의 상태 전이를 이렇게 짰다.

```python
if r.battery < LOW_BATTERY_THRESHOLD:      # 배터리 부족 → 충전 상태로
    r.status = RobotStatus.CHARGING
elif r.status == RobotStatus.CHARGING:     # 충전 중이면 배터리 회복
    r.battery += rng.uniform(0.5, 1.0)
elif rng.random() < 0.001:                 # 가끔 고장
    r.status = RobotStatus.ERROR
```

읽으면 자연스럽다. 6,000틱(=실시간 10분)을 돌려 상태 분포를 찍었다.

```
틱      idle moving charging error  | 평균배터리
    0   1000      0        0     0  |    75.0%
  400     11     59      716   214  |    29.5%
  800      0      0      783   217  |    28.3%   ← 여기서 멈춤
 1200      0      0      783   217  |    28.3%   ← 그대로

충전 중인 로봇의 배터리: 19.97, 19.74, 19.84 …  ← 영원히 오르지 않음
```

**전원이 충전 중이거나 고장난 채로 얼어붙었다.**

원인은 단순했다. `battery < 20`은 **한 번 참이 되면 계속 참인 조건**이다. `if`가 매 틱 걸리므로 배터리를 올려주는 `elif`에 **영원히 도달할 수 없었다.**

더 근본적으로는 **성격이 다른 조건을 한 사슬에 섞은 것**이 문제였다.

```python
if r.battery < 20:          # ← "상태" (계속 참)
elif r.status == CHARGING:  # ← "상태"
elif rng.random() < 0.001:  # ← "사건" (매번 새로 판정)
```

계속 참인 조건이 앞에 오면 뒤가 전부 죽는다. 상태 머신은 **"지금 어떤 상태인가"로 먼저 분기하고, 그 안에서 나갈 조건을 봐야** 각 상태가 자기 코드를 반드시 실행한다.

같이 발견한 것 두 가지:
- **`ERROR`에서 나올 경로가 아예 없었다.** 한 번 고장나면 영원히 고장.
- **고장 확률이 100배 높았다.** `0.001 × 초당 10틱 = 로봇당 초당 1%`. 2분이면 사실상 전부 고장난다(실제로 217대). **틱당 확률을 쓸 때는 틱 빈도를 곱해 초당·분당 빈도로 환산해봐야 한다.**

고친 뒤:

```
틱      idle moving charging error  | 평균배터리
 1000    211    632      157     0  |    65.9%
 3000    220    544      233     3  |    67.0%
 6000    203    552      244     1  |    66.7%   ← 안정 상태
```

계속 흘러가는데 비율은 안정적인, 살아 있는 시스템이 됐다.

#### 2-2. 벡터 성분을 잘못 뒤집은 경계 반사

로봇이 창고(100m × 100m)를 벗어나면 당구공처럼 튕겨야 한다.

```python
if r.x < 0:
    r.heading = (180 - r.heading) % 360      # x 벽
if r.y < 0:
    r.heading = (-r.heading) % 360           # y 벽
```

벽을 향해 달리는 로봇 하나를 지정해 틱마다 좌표를 찍었다.

```
동쪽(heading=90°)으로 가다 오른쪽 벽(x=100)에 부딪힘
  1틱 → x=99.00  heading=90.0
  2틱 → x=98.00  heading=90.0     ← 방향이 안 바뀐다
  3틱 → x=99.00  heading=90.0     ← 벽에 붙어 진동만 한다
```

나침반 방식(북=0°, 시계 방향)이라 속도 벡터가 `(sin θ, cos θ)`다. 따라서:

```
sin(-θ)    = -sin θ,  cos(-θ)    =  cos θ    →  x 성분만 뒤집힘
sin(180-θ) =  sin θ,  cos(180-θ) = -cos θ    →  y 성분만 뒤집힘
```

당구공은 **벽에 수직인 성분만** 뒤집힌다. 그러므로 동서 벽은 `-heading`, 남북 벽은 `180 - heading`이 맞다. **두 공식이 서로 바뀌어 있었다.**

하필 `180 - 90 = 90`이라 테스트한 각도에서 항등식이 되면서, 로봇이 벽에 끼어 진동했다.

고친 뒤:

```
동쪽(90°) → 오른쪽 벽    → heading 270 (서쪽)
북동(45°) → 위쪽 벽      → heading 135 (남동)   ← x는 계속 증가, y만 감소
```

두 번째가 핵심 증거다. **옆으로 가던 움직임은 유지되고 벽에 부딪힌 방향만 뒤집혔다.** 6,000틱 후 1,000대 전체 좌표 범위는 `x 0.04~99.95`, `y 0.02~99.80`으로 전원이 창고 안에 있었다.

#### 이 방법에 대해

두 버그의 공통점은 **문법도 맞고 로직도 그럴듯했다**는 것이다. 코드 리뷰로는 못 잡는다. 필요한 건 **관측 지점을 정하고 시간에 따라 값을 찍어보는 것**이었다.

- 전체 분포를 주기적으로 (`Counter`로 상태별 개수)
- 개체 하나를 지정해 추적 (`fleet[1]`의 좌표를 틱마다)

둘 다 몇 줄이면 되는데, 이걸 안 했으면 "로봇이 잘 도는 것 같다"고 넘어갔을 것이다.

### 방법 3 — 통설을 내 데이터로 재본다

메모리 상태를 담을 `dataclass`에 `slots=True`를 권장받았다. 근거는 "메모리를 40~50% 줄인다"였다.

```
로봇 1,000대   기본 227.7 KB   slots 187.8 KB   → 17% 절약
로봇 5,000대   기본 1.16 MB    slots 0.97 MB    → 17% 절약

속성 읽기 300만회   기본 0.184s   slots 0.112s   → 39% 빠름
```

**메모리 절감은 통설의 절반도 안 됐다.** 이유는 우리 객체가 담은 게 대부분 실제 데이터(문자열 하나 + float 10개)라 `__dict__` 오버헤드 비중이 상대적으로 작았기 때문이다. 필드가 적고 데이터가 작을수록 절감률이 커지는 구조인데, 우리는 반대 경우였다.

속도는 39% 빨라졌지만 절대량으로는 크지 않다.

```
초당 속성 접근 ≈ 1,000대 × 10틱 × 필드 10개 = 10만 회
절약 ≈ 10만 × 24ns ≈ 2.4ms/초   (100ms 예산 중)
```

그래서 `slots=True`를 유지한 **실제 이유는 처음 들은 이유와 달라졌다.**

```python
r.batery = 50      # 오타
# 기본  : __dict__ 에 새 키가 조용히 생김. 에러 없음. 배터리는 안 변함
# slots : 즉시 AttributeError
```

정의에 없는 속성을 못 만든다는 제약이, 파이썬의 유연함이 만드는 대표적인 버그를 막아준다. **성능이 아니라 안전성 때문에 채택한 셈이다.**

같은 방식으로 확률도 확인했다. `rng.random() < 0.1`로 드론을 10% 만들었는데 1,000대 중 98대가 나왔다. 1,000번 시행을 200회 반복해보니 **정확히 100대가 나온 건 200번 중 6번(3%)뿐**이었고 범위는 79~128대였다. "10% 확률"과 "정확히 10%"는 다른 요구사항이고, 코드는 앞쪽을 구현한 것이었다.

시드 고정에 대해서도 오해가 하나 풀렸다. 난수 생성기는 정해진 순서대로 값을 뱉으므로, **코드를 한 줄만 바꿔도**(예: 드론 고도 계산을 추가) 그 뒤 모든 난수가 밀려 결과가 완전히 달라진다.

> 시드 고정은 "같은 코드를 다시 돌리면 같은 결과"를 보장하는 것이지, "특정 숫자가 나온다"를 보장하는 게 아니다.

3주차부터 성능 before/after를 측정할 예정인데, **시뮬레이터 코드를 고치면 이전 측정치와 직접 비교할 수 없다**는 뜻이기도 하다.

## 3. 알게된 것

### 틀린 답에는 공통 패턴이 있었다

4개 모두 **완전히 틀린 답이 아니라, 큰 틀은 맞는데 가정 하나가 검증되지 않은 답**이었다. Enum 답변은 "SQLite에 ENUM 타입이 없다", "TEXT로 저장된다"까지 정확했고 마지막 한 가지(이름이냐 값이냐)만 달랐다.

전부 틀렸으면 바로 알아챘을 것이다. **대부분 맞기 때문에 더 위험하다.** 그리고 내가 처음 다루는 영역일수록 "어디가 검증되지 않은 가정인지"를 짚어낼 감각이 없다.

그래서 이번 주의 결론은 "LLM을 덜 쓰자"가 아니라 **"검증 비용이 낮은 지점을 미리 확보해두자"** 쪽이 됐다. 실제로 세 방법 모두 몇 줄이면 되는 것들이었다.

| 방법 | 비용 | 잡히는 것 |
|---|---|---|
| ORM이 만든 SQL 보기 (`echo=True`, `.schema`) | 설정 한 줄 | 추상화 계층이 몰래 정한 기본값 |
| 시간에 따라 상태 찍기 | 루프 + `Counter` 몇 줄 | 정적 리뷰로 안 보이는 논리 오류 |
| 통설을 내 데이터로 재기 (`tracemalloc`, `timeit`) | 스크립트 10줄 | 조건이 다른 일반론 |

### 검증 도구가 곧 학습 도구였다

`echo=True`를 켜니 내가 쓴 파이썬 클래스가 어떤 SQL로 번역되는지가 그대로 보였다. Enum 문제를 찾으려고 켠 건데, 결과적으로 **ORM이 무슨 일을 하는지 배우는 데 가장 도움이 됐다.**

> "ORM을 쓴다고 SQL을 몰라도 되는 게 아니다" — 문장으로는 알고 있었는데, `CHECK` 제약이 없는 DDL을 눈으로 보고 나서야 의미가 생겼다.

### 검증할 수 없는 부분이 남았다

전부 검증한 건 아니다. 아직 근거를 못 세운 결정들이 있고, 이건 코드를 실행해서 풀 수 있는 종류가 아니었다.

**① 배치 저장 주기 5초.** 실시간 위치는 메모리에 두고 DB엔 5초마다 저장하기로 했다(매 틱 저장하면 로봇 5,000대 기준 초당 5만 INSERT). 그런데 서버가 죽으면 그 5초가 유실된다. "텔레메트리는 관측 데이터라 유실 허용"으로 넘어갔는데, **어디까지가 허용 가능한 유실인지 기준을 못 세웠다.** 주문·결제와 다르다는 건 알겠는데 그 경계를 어떻게 정의하는지 모르겠다.

**② 메모리에 상태를 두면 서버를 2대로 못 늘린다.** 이번 스코프에선 인정하고 가는데, 실무라면 어느 시점에 외부 저장소로 옮겨야 할까. "처음부터 Redis"는 오버스펙 같고 "나중에 옮기자"는 나중이 안 올 것 같다.

**③ 5초 샘플링은 데이터를 버리는 선택이다.** "관제 대시보드의 과거 조회에 100ms 해상도는 과하다"고 판단했지만, 사고 원인 분석 요구가 생기면 근거가 무너진다.

**④ 시뮬레이터의 시간 스케일을 압축했다.** 배터리가 30초면 100%→20%로 떨어진다(실제 로봇이면 몇 시간). 관찰 가능한 시간 스케일로 압축한 건데, "현실성"보다 "데모 가능성"을 택한 셈이다. 시뮬레이션에서 이런 압축은 어디까지 정당할까.

### 다음 주

이번 주 baseline을 남겼다. 3주차에 WebSocket을 붙이고 나서 같은 측정을 다시 할 예정이다.

| 로봇 수 | tick 1회 | 100ms 예산 대비 |
|---|---|---|
| 1,000 | 1.91ms | 2% |
| 5,000 | 5.36ms | 5% |
| 20,000 | 23.07ms | 23% |

시뮬레이터 자체는 병목이 아니다. 전송할 데이터 크기를 미리 계산해보니 로봇 1,000대 전 필드를 초당 10회 보내면 **초당 2.46MB**였고, 화면에 필요한 필드만 소수점 2자리로 줄이면 0.79MB로 68% 줄었다. 다음 병목은 여기일 것 같다.
